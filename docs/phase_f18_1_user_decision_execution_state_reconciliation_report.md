## 1. Executive Summary & Objective

Phase F.18.1 performs a narrow forensic reconciliation of the F.18 state model, user control, auditability, and execution boundaries. Specifically, it reconciles:
1. System Recommendation vs User Decision vs Execution Status separation.
2. P24 exact semantics (System Recommendation = BUY, User Decision = REJECTED, Execution = NOT_EXECUTED, Portfolio = UNCHANGED).
3. P25 exact semantics (System Recommendation = INR 10,000, User Decision = ADJUSTED to INR 5,000, Execution = NOT_EXECUTED).
4. Reassessment system calculation vs User Confirmation application boundaries.
5. Downstream `BUY` interpretation audit (verifying zero silent portfolio mutations).
6. Complete audit reconstructability across `SYSTEM-GENERATED`, `USER-GENERATED`, and `EXECUTION-GENERATED` states.

## 3. Key Reconciliation Findings

### A. P24 Exact Reproduction Semantics
- **System Recommendation:** `BUY` (`final_action_state = ActionState.BUY`).
- **User Decision:** `REJECTED` (recorded in `UserDecisionRecord`).
- **Execution Status:** `NOT_EXECUTED` (no broker/trade execution engine exists).
- **Portfolio State:** `UNCHANGED` (0 holdings, 0 SIPs mutated).
- **Invariant:** A rejected recommendation **never** converts downstream into an accepted action. The system recommendation remains `BUY` in historical logs while the user choice remains `REJECTED`.

### B. P25 Exact Reproduction Semantics
- **System Recommendation:** INR 10,000 SIP contribution (`ACCUMULATE` / `BUY`).
- **User Adjustment:** INR 5,000 user-adjusted contribution.
- **Audit Preservation:** System recommended value (INR 10,000) and user-adjusted value (INR 5,000) remain explicitly distinguished in `UserDecisionRecord`. Zero silent portfolio mutation occurs.

### C. Reassessment vs Confirmation Boundary Clarification
- **Reassessment:** System recalculation triggered by an updated input (e.g., goal target change, income update). Reassessment computes a new versioned assessment ($v_2$) automatically **without requiring user confirmation to perform the math**.
- **User Confirmation:** Required **only** when an investor chooses to apply a recommendation to update their portfolio plan or execute a change.
- **Matrix Correction:** F.18 wording is corrected to clarify: *Reassessment is a system calculation (No user confirmation required to compute $v_2$). Applying/executing recommendation requires explicit confirmation.*

### D. Downstream `BUY` Interpretation Audit
- Static code search and runtime testing confirm: **Zero downstream modules treat `BUY` as an executed trade or automatic portfolio mutation**. `DecisionOrchestrator` operates strictly as a decision-support system.
